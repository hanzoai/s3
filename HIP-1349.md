# HIP-1349: Adaptive Object Compression

## Status
Draft / Research Phase

## Abstract
Integrate an adaptive compression layer into the Hanzo S3 Volume Server based on the PolarStore (FAST '26) methodology. This reduces CPU overhead by skipping compression for high-entropy (already encrypted or compressed) data.

## Motivation
Currently, storage systems often either compress everything (wasting CPU) or nothing (wasting disk). PolarStore demonstrates that a sampling-based "pre-flight" check can accurately predict if a block is worth compressing.

## Specification
1.  **Sampling Layer**: Before writing to the Volume Server, the first 4KB-8KB of an object is sampled.
2.  **Entropy Estimation**: Use a fast, low-overhead compression (LZ4 or Zstd Fastest) on the sample.
3.  **Threshold Logic**: If `compressed_sample / original_sample > 0.90`, the object is marked as `Uncompressible` and stored raw.
4.  **Encryption Boundary**: Compression MUST occur before the `pqproof` or standard AES-GCM encryption layer.

## Metrics & Hypothesis
*   **Hypothesis**: Adaptive compression will show a <5% throughput degradation on compressible data but a >3x throughput improvement on incompressible data compared to "Always-On" compression.
*   **Success Criteria**: 
    *   CPU usage reduction on random data writes.
    *   Zero integrity failures (verified via checksums).
    *   Correctness: Compressed objects must be transparently decompressed on GET.

## Implementation Recommendation
Integrate into `volume_server` logic. When a `PUT` request arrives, the `Filer` or `Volume Server` performs the sampling. The result (Compressed vs. Raw) is stored in the Needle header.
